# Disappearing messages and one-time photos

Conversation disappearance settings are visible to both accepted participants. Either may set an hourly duration between one hour and thirty days or turn it off; changes apply only to new messages. A ten-second cooldown prevents setting spam. The backend stamps deadlines when a message is sent; clients cannot choose timestamps, extend an existing message's life, or update its privacy mode.

At the deadline, RLS denies message text, photo metadata and regular photo downloads to both participants. Moderator queues and photo review do not bypass expiration. Reporting cannot newly share expired content. The app receives server time with each bounded history page and computes a conservative monotonic deadline, subtracting request latency, rather than trusting the phone's wall clock. Cached content and copies already delivered cannot be recalled from a modified client or another camera.

One-time photos use a reservation flagged before uploading, the existing trusted JPEG processing pipeline and private Storage. Ordinary Storage reads are denied for everyone, including the sender and moderators. The `open-photo` Edge Function verifies the bearer with Auth.getUser and atomically claims the first recipient opening under account/conversation/asset locks. Only the recipient of the sent photo may claim it; concurrent requests have at most one winner. The endpoint returns non-cacheable JPEG bytes, never a reusable signed URL, token or Storage path. A delivery interruption consumes that opening: retrying cannot reopen it. This tradeoff must be disclosed before opening.

The viewer is implemented on the existing protected navigation window, not a separate native dialog that could lose Android secure-window flags. Native capture prevention remains on for all chats. The one-time viewer clears on leaving/backgrounding and has a maximum sixty-second session. It must not persist image data in files, navigation parameters or global state. An external camera or compromised/rooted device cannot be controlled by this app; no absolute capture-prevention or E2EE claim is made.

Physical cleanup uses the existing mark → Storage API delete → metadata finalize order. Expired attached photos are immediately eligible; consumed one-time photos receive a five-minute cleanup grace to avoid racing delivery. A consumed photo's message remains an opened placeholder until its own expiry. Expired text and expired-photo messages are removed, and their reports cascade. For thirty days, private delivery tombstones retain only message ID, sender ID, conversation ID and send/removal times; no body, digest or photo path is retained. They prevent stale delivery retries from resurrecting erased content and preserve rolling send quotas. They cascade on account/conversation deletion and are purged after thirty days by maintenance.

Existing messages have no expiry and existing photos remain regular unless explicitly sent using the new feature. No existing conversation content is automatically assigned a new deadline. Backend deployment precedes UI enablement; old clients cannot bypass the new access rules. Scheduled physical maintenance and the UI are verified as subsequent phases; database denial at expiry is independent of scheduler health. Backups/provider retention and recipients' prior copies remain outside live-object cleanup.

## Verification

Embedded Postgres tests exercise real migrations, recipient-only claims, direct Storage denial, expiry for both participants, physical-delete ordering, tombstones and quota preservation. Handler tests cover bounded inputs, denied browser/anonymous requests, one-time binary delivery and sanitized failure. Full-service CI additionally tests concurrent opens, actual private Storage bytes and account/session authorization. No hosted ephemeral content is changed during deployment smoke checks.
