# Private profile photos and fresh chat history

Account → Your profile photo lets a member choose a photo, change it, or remove/reset it. The mobile app resizes to a maximum 320-pixel side. A trusted server decodes/re-encodes JPEG pixels, discards submitted metadata and limits stored output to 256 KB. Upload reservations are one-use and server limited to five attempts per day and twenty unpurged reservations. Private thirty-day reservation metadata preserves limits after replacement/deletion; it contains IDs/times/paths, not image bytes. Account erasure cascades these records.

The `profile-photos` bucket is private. Only the current validated photo is readable by its owner and accepted, unblocked contacts while both accounts are enabled. Pending invitations, outsiders, anonymous clients and blocked contacts cannot download it. There are no public or signed URLs, external image hosts, client writes or broad gallery permissions. Home, Friends, chat and Account display authenticated images without disk caching. Missing/unavailable photos fall back to the first character of the first name. Contacts see changes after returning to the screen or refreshing chat; online/live-profile synchronization is not claimed.

Replacing or removing a photo revokes old reads before cleanup. Storage API deletion precedes marking metadata purged. Cleanup failures remain retryable through Remove/reset or a subsequent successful upload; stale abandoned reservations are eligible after an hour. Automatic monitoring remains a separate release requirement. Account erasure freezes uploads using the same profile lock, removes all the account's profile-photo bytes, and only then deletes Auth/metadata. It does not remove other people's profile photos. Copies already delivered and provider backups cannot be recalled.

Conversation settings → Clear chat for both people requires a destructive confirmation. It clears only that shared conversation, including text, regular and one-time photos and associated reports, while keeping the connection and retention setting. Nothing is automatically wiped from the hosted project. Service-only operations verify the Auth.getUser actor and accepted/unblocked membership; direct clients cannot freeze or finalize a chat. A conversation lock freezes message/photo insertion; marked assets deny reads and trusted uploads. Physical Storage removal precedes final message/asset deletion. Failure leaves a visible pending state with a Retry action, never a false success. Idempotent request records and private message delivery tombstones prevent a response retry or an old send retry from wiping new history or resurrecting cleared messages. Tombstones and request metadata retain at most thirty days until a subsequent maintenance/finalization pass; they contain no message body or image bytes.

The app is access-controlled, not end-to-end encrypted. Screenshot testing remains an explicit development-only opt-in; release capture prevention is unchanged.

## Device checklist

1. Confirm old unexpired regular photos render inside bounded bubbles; consumed/expired one-time media must remain unavailable. Check both sender and recipient layouts, long captions and large system text.
2. Open retention settings, choose presets, switch 24 hours ↔ 1 day, and verify only Save applies changes. The panel must stay open after saving. Return from viewing/reporting a photo and from other screens; scroll should restore. New chat entry starts at recent messages, and new messages follow only while near the bottom.
3. Use disposable content to Clear chat. Read the confirmation: both accounts lose shared history. Verify the connection stays, both views are empty after refresh, and a fresh message/photo works normally.
4. Add, replace and remove a profile photo. Return to Home/Friends and refresh chat on the other phone. Without a photo, check the first-name initial. Block the contact and verify their photo is no longer accessible after refresh.
5. Recheck keyboard/password/autofill, sign-out/account switching, one-time background closure and account deletion with disposable accounts. With screenshot testing disabled, repeat screenshot, recording and recent-apps checks. Signed-build/iOS testing remains separate.

SQL/handler tests and real-service CI cover authorization, one-use upload claims, codec limits, physical-delete ordering, retry failures, quota preservation, shared clearing and account erasure. Successful bundles do not establish native layout/OS behavior on the owner's phones.
