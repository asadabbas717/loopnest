# Trusted processing of new photos

New photo uploads go through the authenticated `upload-photo` Edge Function. Direct client Storage INSERT is disabled. The phone still resizes selected images to at most 1280 pixels on each side and 1 MiB before sending; those checks improve usability but are not trusted for authorization or file safety.

The function explicitly verifies the bearer with Supabase Auth, then uses a service-only database function to claim a reservation owned by that user. The reservation must be fresh, in an accepted available conversation, and not already attempted, erasing or selected for cleanup. Existing per-account reservation limits apply before CPU-intensive validation. Each claim is usable once, including invalid input; choose the photo again after a failed/lost upload response. Failed attempts still count toward the daily quota and are eligible for abandoned-photo cleanup after 48 hours.

The function reads a bounded binary JPEG stream (at most 1 MiB), checks frame dimensions before decoding, fully decodes pixels with strict decoding, a 1.7-megapixel ceiling and a 64 MiB decoder allocation limit, then encodes a new JPEG from only RGBA pixels/dimensions. The input's EXIF/GPS, comments, application markers and trailing bytes are not forwarded. Re-encoded output must also fit 1 MiB. Supabase's 2-second request CPU limit remains an outer bound; a runtime termination cannot mark an upload validated. Maximum-size codec tests pass locally, but they are not a performance guarantee for every hosted request.

The pinned codec is `jpeg-js@0.4.4`, installed only for server/unit testing and imported by exact version in the Edge Function. It is not imported into the mobile bundle. Version 0.4.4 contains the published infinite-loop fix; review future advisories and maintain the dependency. Its BSD notice is preserved in `THIRD_PARTY_CODEC_LICENSE.txt`. Relevant primary references: [codec API](https://github.com/jpeg-js/jpeg-js), [published fix](https://github.com/advisories/GHSA-xvf7-4v9q-58w6), [Edge runtime limits](https://supabase.com/docs/guides/functions/limits).

The function stores only processed bytes with the service key in server memory and then marks the asset validated. A database trigger prevents attaching a new unvalidated asset to a message. Trusted Storage inserts lock/recheck the conversation and reservation, including account erasure, blocking, expiration and cleanup. Service uploads do not bypass this freeze check. Storage/finalization failure reports failure and leaves only an unattached retry/cleanup candidate, not a successful message. Raw input is not deliberately persisted to a quarantine bucket or logged.

The mobile upload binds to its initiating account, checks that the returned reservation belongs to that account, and passes the captured bearer explicitly to the function. Switching accounts during reservation cannot silently upload old-account bytes into a new-account asset. These checks complement the existing expected-sender guard on message submission.

## Deployment and compatibility

Deploy `upload-photo`, apply `202610220003_validated_photos.sql`, and reload the updated app before testing new uploads. As with deletion, gateway `verify_jwt=false` delegates validation to the explicit Auth.getUser check inside the handler; it is not anonymous upload access. The service key never reaches the phone. Older clients that upload directly are denied after the migration. Existing messages/photos remain accessible to their authorized participants; they are **legacy uploads**, not retroactively validated or claimed to have server-stripped metadata.

No image transformation subscription, external image service or paid worker is used. This consumes the project's Free Edge Function/storage allowances and fails when quotas or runtime limits are reached. It is file validation/re-encoding, not malware-proof processing, semantic abuse detection, E2EE or a complete security assurance. Human moderation, aggregate abuse controls/quota monitoring, broader image-format/device tests, dependency fixes and independent review remain release work.

## Tests

Unit tests execute the real codec against injected EXIF, comments and trailing payload, malformed/truncated data, excessive byte/dimension bounds and maximum native resize dimensions. Handler tests cover auth/ownership, ordering, byte/MIME rejection and persistence failure. Database tests forbid direct upload, client validation flags, attaching unvalidated bytes and trusted writes into a blocked conversation. The real integration suite uses the same mobile upload API and tests successful processed-photo delivery, forged input, outsider claims, claim reuse and the streaming size limit alongside erasure, moderation and cleanup. See `STATUS.md` for verified execution evidence.

The function and migration are deployed to the dedicated Free test project. After reloading Expo Go, test sending an ordinary camera photo and a large gallery photo between the disposable accounts, opening each from the other account, and confirming older shared photos still open. Hosted CPU performance and broader device/format behavior remain acceptance checks; no real hosted photo was submitted by the deployment smoke checks.
